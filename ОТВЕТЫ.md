## Часть A. Почему так

### A1 — почему изменилось и у `a`
потому что a и b — это не два разных объекта, а две ссылки на один и тот же объект в памяти, условно говоря два объекта а и b отвечают за одну и ту же ссылку: изменили а - поменяется b и наоборот.


### A2 — почему `3` раньше `2`
Promise имеет приоритет над setTimeout


### A3 — почему счётчик остался нулём
Когда вызывается counter.add, js заходит внутрь стрелочной функции и пытается выполнить this.n += 1, а так как стрелочная функция () => {} не создает свой контекст выполнения, она берет this из внешнего окружения, а это глобальная область видимости. В глобальной области видимости this — это объект window, a значит код внутри add на самом деле делает window.n += 1. counter.n никак не затрагивается и остается равным 0

## Часть B. Что было не так

Четыре находки. По каждой: в чём была проблема и что вы исправили.

### Ошибка 1

**Было не так:**
id приходит из item.dataset.id. dataset всегда возвращает строку, типо в функцию приходит строка "1", а в массиве tasks id — это числа (1, 2, 3).Строгое равенство t.id === id (число === строка) всегда даёт false.
find возвращает undefined, indexOf возвращает -1, и splice(-1, 1) удаляет последний элемент массива, независимо от того, какую кнопку нажали.

**Исправил:**
нужно приводить id к числу при сравнении или при передаче
const task = tasks.find((t) => t.id === id); //неправильно
const task = tasks.find((t) => t.id === Number(id)); //правильно


### Ошибка 2

**Было не так:**
метод sort без аргументов приводит элементы к строкам и сортирует их по алфавиту. Массив состоит из объектов поэтому они превратятся в строку и сортировка ничего не изменит и плюс мы же хотим сортировать по важности а не по алфавиту

**Исправил:**
просто передадим компаратор
tasks.sort();// неправильно
tasks.sort((a, b) => b.priority - a.priority); // правильно

### Ошибка 3

**Было не так:**
обработчик клика filterBtn
метод filter не меняет исходный массив, а создаёт и возвращает новый массив с отфильтрованными элементами. Поскольку результат никуда не сохраняется то исходный массив tasks остается прежним и на экране ничего не меняется.

**Исправил:**
перезаписал исходный массив результатом фильтрации
tasks.filter((task) => task.priority >= 5); //неправильно
tasks = tasks.filter((task) => task.priority >= 5); //правильно

### Ошибка 4

**Было не так:**
обработчик кликов по всем кнопкам
функция createCounter вызывает замыкание и создаёт локальную переменную count = 0, но мы вызываем createCounter внутри обработчика клика, это значит что при каждом клике счётчик создаётся заново с нуля увеличивается на 1 и возвращает 1 а count не сохраняется между кликами

**Исправил:**
создал счётчик один раз снаружи чтобы он жил в замыкании и сохранял своё состояние между кликами

## Часть C. Обоснуйте выбор

### C1 — какой вариант карточки и почему

**Выбираю:**
второй

**Причины:**
второй вариант с тегом `<a href="">`, потому что он работает как настоящая ссылка из коробки тобишь на него можно перейти с клавиатуры через Tab и нажать Enter, а на обычный `<div>` с `onclick` клавиатурой не перейти без дополнительных костылей, плюс на ссылке работает правый клик мыши с опциями "открыть в новой вкладке" и "скопировать ссылку", чего нет у `<div>`. Вдобавок тег `<a>` понятен скринридерам, тогда как `<div>` для программ чтения с экрана остаётся просто текстовым блоком, `<a>` это семантически правильный способ навигации, а инлайновый `onclick` в первом варианте смешивает HTML с ДЖС и считается плохой практикой.

### C2 — какой вариант вывода списка и почему

**Выбираю:**
второй

**Причины:**
 имена вводят сами пользователи, а значит они могут содержать вредоносный код. Если использовать первый способ браузер воспримет введённый текст как HTML и хакер сможет внедрить скрипты типо хсс атак и тд тогда как `textContent` во втором варианте выводит любые данные строго как обычный текст делая код безопасным. второй способ работает быстрее и надёжнее тобишь он создаёт реальные элементы в памяти браузера а не заставляет его заново парсить всю HTML строку целиком.
